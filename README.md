# NAC Fuel Management System

A national, multi-airport aviation fuel management platform prototype for the
Papua New Guinea National Airports Corporation (NAC).

> **Prototype / design disclaimer** — this is a software prototype and MVP.
> It is **not** an officially approved NAC operational system, and it does
> **not** claim aviation regulatory compliance. Aviation fuel standards,
> safety requirements and operational procedures referenced in this codebase
> are configurable placeholders that require validation by NAC, CASA PNG and
> qualified aviation/fuel specialists before any real-world use. All seed
> data is fictional — **DEMO / NOT REAL NAC DATA**.

## What this is

An end-to-end digital chain covering:

```
Supplier → Receipt → Storage Tank → Transfer → Refueller/Bowser →
Aircraft Uplift → Billing → Reconciliation → Audit → Reporting
```

The MVP implements this workflow **functionally**, not as static screens —
see [MVP Status](#mvp-status) below for exactly what runs today versus what
is scaffolded for later phases.

## Quick start (local dev)

Requires Node.js 20+.

```bash
# 1. Install and run the API (SQLite-backed for zero-infra local dev)
cd apps/api
npm install
npm run seed     # loads realistic fictional demo data
npm run dev      # http://localhost:4000

# 2. In a second terminal, run the web app
cd apps/web
npm install
npm run dev      # http://localhost:5173 (proxies /api to :4000)
```

Log in with the seeded demo account:

```
email:    admin@nac.gov.pg
password: Password123!
```

Other seeded accounts (`{role}@nac.gov.pg`, same password) let you explore
role-based access — e.g. `pom.operator@nac.gov.pg` (Fuel Operator, POM
airport) or `finance@nac.gov.pg` (Finance Officer).

### Docker Compose

```bash
docker compose up --build
```

Brings up the API and web app together. See `DEPLOYMENT.md`.

## MVP status

Per the build brief's own instruction: **do not describe unimplemented
features as implemented.** Here is the honest state of this prototype.

### Fully implemented and verified working end-to-end

- Authentication (JWT + refresh) and RBAC across 11 roles
- Airport master data (create/edit/activate — not hard-coded)
- Tanks, refuellers, fuel products, suppliers, airlines, aircraft
- **Fuel receipt workflow**: Draft → Submitted → Verified → Approved → Posted,
  posting to the immutable inventory ledger
- **Fuel transfers**: tank↔tank, tank↔refueller
- **Aircraft uplift**: the core atomic transaction — validates stock/aircraft/
  refueller, deducts inventory, generates an invoice, writes an audit
  record, all inside one database transaction with rollback on failure
- **Inventory ledger**: every movement is an immutable row; balances are
  derived and cached; negative stock and over-capacity are rejected
- **Reconciliation engine**: computes expected vs. actual closing stock,
  flags variance beyond a configurable threshold, raises alerts, requires
  an explanation to approve
- Billing (invoice generation, issuing, payments)
- Fuel quality tests, maintenance records, alerts, audit log
- National and airport-level dashboards with live aggregated data and charts
- Map view (status beacons plotted from airport coordinates)
- IoT device/reading endpoints with simulated data

This was verified by seeding realistic demo data and exercising the API
directly (login → uplift → inventory deduction → invoice generation),
confirmed against actual before/after balances.

### Present but intentionally simplified for the MVP

- **Database**: runs on SQLite for zero-infrastructure local development.
  The full production PostgreSQL schema exists at
  `database/migrations/001_init.sql` and is the schema of record; porting
  the API's data access layer from `better-sqlite3` to a Postgres driver
  (e.g. `pg` or `Prisma`) is mechanical but not yet done.
- **Controller/service/repository layering**: routes call services directly
  for most CRUD endpoints; the five business-critical engines (inventory,
  receipts, transfers, uplift, reconciliation) are properly isolated in
  `apps/api/src/services/` and are independently testable, per the brief's
  priority on business logic separation.

### TODO / future integration (explicitly not built)

- **Offline sync engine**: the local-store → sync-queue → conflict-resolution
  pipeline described in `OFFLINE_SYNC.md` is designed but not implemented.
  The `sync_queue` table exists in the schema as a landing point for this work.
- **Live IoT ingestion**: `/api/v1/iot/readings` is a simulated ingest
  endpoint standing in for the MQTT → Gateway → Broker → Telemetry Service
  pipeline described in `IOT_INTEGRATION.md`.
- **CI/CD pipeline**: described in `DEPLOYMENT.md`; a sample GitHub Actions
  workflow is included, but no security-scanning or staging environment is
  wired up.
- **System Settings UI**: business rules are currently read from
  `.env` / documentation, not from an editable in-app settings table.
- **MFA**: the `users.mfa_enabled` column and password hashing are in place;
  actual TOTP/MFA enrollment flow is not implemented (architecture is
  MFA-ready per the brief's requirement, not MFA-complete).
- **PDF/CSV report export**: report data is available via API and rendered
  in-app; file export is not yet wired up.
